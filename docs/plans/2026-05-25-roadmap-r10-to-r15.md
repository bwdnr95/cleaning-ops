# Cleaning Ops Control Center — Production Roadmap (R10 ~ R15)

> **작성자**: CTO  
> **작성일**: 2026-05-25  
> **컨텍스트**: R1–R9 (운영팀 요청서 + 다중라인 주문 + 자동공개 + soft-delete + 24h 세션 + Postgres + admin-only 진입 + 단일 포트 8002) 완료. R8 cross-review APPROVED. 운영팀이 단일 도메인(`cleanjob.tono-operation.com`)으로 운영 중.  
> **목적**: 운영팀 요청 사항(PDF 등)과는 **별개**로, 이 시스템이 production으로서 부끄럽지 않게 동작하기 위한 추가 기능/인프라 보강. "내 이름을 걸고 하는 첫 사이드 프로젝트"라는 품질 기준을 충족.

## CTO 시점에서 본 현재 시스템의 빈틈

R9까지 마치고 나면 **기능적으로는** 청소 운영 워크플로우가 끊김 없이 돈다. 그러나 production-grade 시스템이 갖춰야 할 다음 8가지가 부재하거나 불완전하다:

1. **인증/세션 보안** — access/refresh 토큰을 `localStorage`에 저장. XSS 1건이면 모든 세션 탈취. R8 자체 review에서 trade-off로 인지했지만 보류된 상태.
2. **메시지 발송** — `MessageProvider`는 추상화돼 있지만 실제 발송은 `MockMessageProvider`. 운영 시 알림톡이 안 나간다. SOLAPI config 변수만 .env에 박혀 있음.
3. **파일 저장소** — 사진은 `backend/local_storage/`에 그대로. 서버 재배포/장애 시 사진 분실. CDN 없음.
4. **백업/복구** — Postgres 자동 백업 0. 운영자 실수 1건이면 데이터 영구 소실.
5. **관측/장애 감지** — Sentry config 변수만 있고 wiring X. 에러가 발생해도 운영자가 직접 보고하기 전까지 모름. structured logging도 없음.
6. **CI/CD** — main 브랜치에 push되면 사용자가 직접 ssh로 들어가 빌드/재시작. 테스트 실행도 수동. 실수 한 번이면 운영 다운.
7. **PII 보호** — 고객 이름/전화/주소가 평문 저장. 정보주체 권리 요청 절차 없음. 한국 PIPA 기준 미달.
8. **운영 통계/리포트** — 운영팀이 매월 정산할 때 엑셀 export가 없어 직접 SQL 두드려야 함. 협력사별 성과·매출 추세 등 의사결정 정보 부재.

## 우선순위 결정 기준

본업(tono-operation)과 병행, 사이드 프로젝트 시간 한정, "쪽팔리지 않게"라는 품질 기준을 함께 만족하려면 다음 원칙을 따른다:

- **운영 중에 실수 1건이 데이터 손실/사고로 직결되는 항목**부터.
- **운영자가 매일 쓰는 흐름의 빠진 조각**을 그 다음.
- **외부 데모/검수 시점에 가장 먼저 눈에 띄는 약점**을 동시에 보강.
- **codex가 task-by-task로 실행 가능한 단위**로만 쪼갠다 — 한 R 마일스톤은 1~2주 분량.

### R10 — Production Foundation (별도 plan 작성)

### R11 — Real Message Delivery

**Goal:** `MockMessageProvider` 자리에 SOLAPI 알림톡/SMS 실제 발송이 들어간다. 발송 실패가 운영팀에게 즉시 가시화된다.

**핵심 작업:**
- `app/services/messages.py`의 `SolApiMessageProvider` (이미 일부 구현 존재 가정) 완성 + signature/headers 검증.
- 알림톡 4 종 (`customer_schedule_confirmed`, `customer_day_before`, `partner_assignment`, `customer_photo_ready`) 템플릿 ID를 `.env`에서 읽도록.
- 발송 실패 시 지수 백오프 retry (최대 3회) — 새 worker 도입 X, 동기 retry로 충분.
- 발송 실패가 `message_logs.status = FAILED`로 기록되면 운영팀 알림 (Sentry breadcrumb + 관리자 대시보드의 "발송 실패" 카드).
- 발송 비용 추정 컬럼 (`message_logs.estimated_cost_krw`) + 월별 집계 view.
- 알림톡 → SMS 자동 fallback 정책 (이미 `solapi_alimtalk_fallback_sms` config 있음).
- 알림톡 발신 프로필(`solapi_kakao_pf_id`) 운영 등록 절차 runbook.

**의존성:** R10 완료 (Sentry wiring이 retry 실패 추적의 전제).

**테스트:** 발송 unit (mock SOLAPI HTTP), 실패 retry, fallback, 비용 집계.

### R12 — Object Storage + Image Pipeline

**Goal:** 사진이 S3/Cloudflare R2에 저장되고 CDN으로 서빙된다. 협력사가 올린 사진은 자동 썸네일 + WebP가 만들어진다. 고객/협력사는 signed URL로만 접근.

**핵심 작업:**
- `app/services/storage/` 에 `S3Storage` 구현 (boto3 또는 aioboto3). `LocalStorage`와 인터페이스 통일.
- 환경 변수로 provider 스위치 — `storage_provider=s3` (config 이미 존재).
- 사진 업로드 파이프라인:
  - 원본 저장
  - Pillow로 1024px long-edge 리사이즈 + WebP 인코딩 → `_thumb` suffix
  - 두 객체 다 저장, DB에는 둘 다 reference
- 고객/협력사 응답 DTO에 signed URL 반환 (TTL 1시간).
- CDN 캐싱: Cloudflare에 origin → S3 연결, 캐시 정책 `max-age=86400`.
- 로컬 마이그레이션 스크립트: `scripts/upload_local_storage_to_s3.py` — 기존 `local_storage/`의 파일을 S3로 일괄 업로드 + DB의 `file_url` 갱신.

**의존성:** R10 (Sentry로 업로드 실패 추적).

**테스트:** 업로드 → 썸네일 생성 → signed URL 발급 → CDN cache hit.

### R13 — Operational Reporting

**Goal:** 운영팀이 매월 정산할 때 엑셀 두드리지 않는다. 협력사·서비스·기간별 매출/작업수가 한 화면에서 보인다.

**핵심 작업:**
- 신규 admin 메뉴 `보고서` (사이드바 추가).
- 화면 4종:
  - **매출 추세** — 일/주/월 단위 line chart, partner_id/service_id 필터.
  - **협력사 성과** — 협력사별 작업 수, 평균 단가, 정산 미입력 건수.
  - **서비스 인기** — service_item별 작업 수, 매출 점유율.
  - **정산 대기 목록** — partner_payment_status가 미정산인 주문 일괄.
- export: 위 4 화면 모두 CSV/Excel 버튼. xlsx는 `openpyxl`.
- 대량 import: `POST /api/admin/orders/import` (xlsx 업로드 → 행별 validate → 일괄 그룹 생성). 실패 행 리포트 반환.
- 차트 라이브러리: `recharts` (React 19 호환, gzip 50KB 미만).

**의존성:** 없음 (R10 권장).

**테스트:** 통계 SQL 정확성, import의 부분 실패, export 컬럼 일관성.

### R14 — Partner Mobile Upgrade

**Goal:** 협력사가 본인 휴대폰에 "앱처럼" 설치해 쓴다. 배정/취소 시 푸시 알림이 온다. 월말 정산이 PDF로 자동 생성된다.

**핵심 작업:**
- PWA: `manifest.json` + service worker (Workbox), 홈 화면 추가 가능.
- Web Push (VAPID 키 발급, 협력사별 구독 저장 테이블 `partner_push_subscriptions`).
- 알림 트리거: 배정/일정변경/취소/공지.
- 협력사 통계 화면: 이번달 작업수/예상수익/완료율.
- 정산서 PDF: `weasyprint` 또는 `reportlab`으로 월별 정산 PDF 생성, 협력사 화면에서 다운로드.
- 오프라인 캐시: 작업 카드 read-only로 캐시 (사진 업로드는 온라인 필수).

**의존성:** R12 (사진 CDN으로 PWA 캐시 안정성↑).

**테스트:** PWA 설치 가능, push 발송, PDF 정합성 (소수점/단위/날짜).

### R15 — Privacy & Compliance

**Goal:** 한국 PIPA 기준에 부끄럽지 않은 수준의 PII 보호. 정보주체 권리 요청에 대응할 수 있는 구조.

**핵심 작업:**
- PII 암호화 (at rest): 고객 전화/주소를 SQLAlchemy `TypeDecorator`로 AES-256 GCM 암호화. 키는 환경변수 + KMS(가능 시).
- 약관/개인정보처리방침 페이지 (admin 사이드바 푸터 + customer 페이지 푸터).
- 쿠키 알림 배너 (한국법은 약함이지만 형식적으로).
- 감사 로그 UI: 관리자가 `audit_logs`를 누가/언제/뭘 조회/수정했는지 볼 수 있는 화면.
- 데이터 보존/삭제 정책: 완료 후 N개월 지난 주문은 PII만 익명화 + 통계용 메타데이터만 보존.
- 정보주체 권리 API: 고객 token으로 본인 데이터 export(JSON) + 삭제 요청.

**의존성:** R10 완료 (감사 로그가 의미 있으려면 logging 기반 필요).

**테스트:** 암호화 round-trip, 보존 정책 batch, 정보주체 export 정확성.

## 운영 모드 변경 — 어떻게 codex와 일할지

본업 부담을 고려해, 마일스톤마다 다음 사이클을 반복한다:

```
1. CTO(나/Claude) 가 plan 문서 작성 — task-by-task TDD 형식, codex가 그대로 실행 가능.
2. Codex CTO 사전 리뷰 (read-only) — 5단계: VERDICT/BLOCKING/SHOULD/NITS/NOTES.
3. BLOCKING 해소 → APPROVED 받을 때까지 loop.
4. Codex가 plan 실행 — 각 task 끝마다 git commit, 회귀 테스트 통과 확인.
5. Cross-review (Claude 직접 + Codex 양쪽) — 코드 결과물 검증.
6. 발견된 SHOULD FIX는 다음 hot-patch 묶음.
7. main 브랜치 머지, 사용자(=나)가 8002에 backend 재시작 + frontend build → 운영 반영.
```

이 사이클은 R8/R8.5에서 이미 정착됨 (`MEMORY.md`의 cross-review pattern, single-port-8002-deployment).
