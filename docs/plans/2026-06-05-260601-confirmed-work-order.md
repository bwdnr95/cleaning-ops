## 1. 🟡 주문 상태 5개 → **4개 + 취소** (WO#3) — 최대 난이도

### 확정 사항
- **작업완료를 클릭하면 잔금 안내 문자가 자동 발송**된다. 따라서 원안 ③ "작업완료(잔금미안내)" 구분은 **불필요** → 삭제.
- "취소"는 **별도 표시로 유지**.
- 결과적으로 **화면 표시 상태 = 4개 + 취소**:

| 표시 상태 | 내부 OrderStatus(13종, 그대로 유지) |
|---|---|
| ① 일정/협력사 확인중 | 신규접수, 상담중, 협력사확인중, 일정확정, 전날안내필요, 전날안내완료 |
| ② 작업확정 | 작업예정, 작업진행, 사진검수대기 |
| ③ 작업완료(잔금 안내) | 고객전달필요, 고객전달완료 |
| ④ 최종결제완료 | 서비스완료 (+ 결제 완납) |
| (취소) | 취소 |

### 구현 방향 (가역·저위험 원칙)
- **내부 13상태를 물리 삭제하지 말 것.** 사진 자동공개/검수 invariant, timeline `status_changed`, 메시지 트리거가 내부 상태 문자열에 결합돼 있음. **표시(presentation) 레이어에 5(→4)버킷 매핑만 추가**한다.
- 신설: `frontend/src/domain/orderStatus.ts`에 `OPERATIONAL_STAGES` + `toOperationalStage(order)` 매핑. 목록 탭/배지, 상세, 캘린더 `statusTone` 노출만 버킷으로 단순화.

### ★ 핵심 변경 — 작업완료 시 잔금 안내 문자 자동 발송
- 현재 `complete_partner_job`(`backend/app/services/orders.py:359-393`)은 `IN_PROGRESS → 고객전달필요`만 하고 **메시지 발송이 없다.**
- 변경: **작업완료 전환 시 고객에게 "작업완료 + 잔금 안내" 메시지를 자동 발송**하고, `message_logs` + timeline(`message_sent`) 기록.
- **🔴 착수 전 1건 확정 필요**: 자동 발송할 메시지 타입.
  - 현재 잔금 전용 타입이 없음. 후보: (a) `CUSTOMER_PHOTO_READY`(고객링크 안내, 고객 화면에서 잔금 확인) 재사용, (b) `CUSTOMER_QUOTE`(잔금 변수 보유), (c) **신규 `customer_balance_due` 타입 + 템플릿 신설**(권장 — 의미가 정확하고 SOL-API 템플릿 분리 가능).
  - 메시지 4종 + 추가 타입은 `domain/constants.py`·`domain/message_templates.py` 중앙 정의로만 추가.
- "작업완료" 트리거가 **협력사 액션**(`complete_partner_job`)인지 **관리자 액션**인지 확인: 두 경로 모두에서 자동 발송이 일어나도록 훅 위치 정리. 발송 실패도 `message_logs`에 남기고, 발송 실패가 상태 전환을 막지 않게(베스트에포트) 처리.
- ③ 표시 판정: `status ∈ {고객전달필요, 고객전달완료}` 이면 ③. (자동발송 성공 여부와 무관하게 "작업완료" 진입 시 ③로 보이되, 발송 실패 건은 관리자에게 재발송 가능하도록 #5 진행 신호와 연동.)

### 수용 기준
- 목록/상세/캘린더에서 4버킷 + 취소로 노출. 내부 플로우·사진·메시지·timeline 정상 동작.
- **작업완료 처리 시 고객 잔금 안내 메시지가 1회 자동 발송**되고 로그/타임라인에 기록.
- 기존 테스트 통과 + 매핑 단위테스트 + 자동발송 테스트 추가.

> ⚠️ ②/⑤ 간 enum, 메시지 자동발송은 **#5(진행 신호)·#2(미수금)와 정합**해야 함. 설계 시안 1개 CTO 컨펌 후 착수.

## 9. 🟡🔴 도급가 부가세 포함 일괄 변경 + 별도/포함 표시 (WO#13 + WO#14) — ⚠️ 데이터 마이그레이션, 고위험

### 확정 사항
- 도급가를 **부가세 포함 금액으로 일괄 변경**. **대상 = 전부.**

### 🔴 착수 전 최종 확정 필요 (되돌리기 어려움 — 반드시 컨펌)
- (a) **현재 저장된 도급가가 "부가세 별도"가 맞는지** 명시 확인. (별도여야 ×1.1. 이미 포함이면 중복 과세) — 도급사가 "포함으로 일괄 변경"을 요청 = 현재 별도 전제로 이해하나, **실행 전 1줄 확정** 필요.
- (b) 세율 **10%** 확정.
- (c) **정산 완료(`partner_settled_at` 존재 / `PartnerPaymentStatus.PAID`) 주문은 제외 권장** — 정산 끝난 건 변경 시 정산/보고서 정합성 파괴. "대상 전부" 지시와 충돌하므로 **dry-run 리포트로 제외 범위 CTO 최종 확정.**

### 구현 방향(필수 가드 — 모두 충족해야 실행)
- 일회성 스크립트(`backend/scripts/`): 대상 = `service_item.partner_base_price` + `order.partner_payment_amount` 전부.
- **Decimal 반올림 규칙 명시**(원 단위), 부동소수점 금지.
- **before-snapshot**: 변경 전 값 CSV/백업 테이블 저장.
- **dry-run diff**: 적용 전 대상 건수·전후 값·합계 차이 리포트 → 검토 후 실제 적용.
- **rollback**: 되돌리는 SQL/절차 문서화.
- 적용 후 `reports.py`/`partner_settlements.py` 합계 전후 비교.
- **(WO#14) 도급가 별도/포함 표시**: `order`(필요 시 `service_item`)에 `partner_vat_type`(VatType) 컬럼 추가(Alembic `0011_`), admin DTO/폼 노출(협력사/고객 비노출). 일괄변경 후 기본값 = **포함**. 도급가 표시 지점(#4 상세, 협력사 배정 섹션, 목록 배지)에 별도/포함 뱃지.

### 수용 기준
- 백업 + dry-run 통과 + CTO/도급사 승인 후에만 실제 적용. 정산완료 제외(확정 시). 도급가에 별도/포함 표시 일관. #4 이윤 계산이 변경된 도급가 기준으로 정확.

> ⛔ 무지성 ×1.1 금지. dry-run·백업·승인 없이는 실 데이터 변경 금지.
