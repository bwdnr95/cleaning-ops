## 0. 합의된 결정
- **#2**: 요청에 `payment_status=paid`가 있고 **운영자가 같은 요청에서 상태를 직접 지정하지 않았으며** 현재 상태가 **취소·서비스완료가 아니면** → `status=서비스완료` 자동. **어떤 작업 상태든 적용**(작업 전 건도; 매출·정산 즉시 반영은 사용자 수용).
- **#3**: 요청에 `status=서비스완료`가 있고 **운영자가 같은 요청에서 결제를 직접 지정하지 않았으며** 현재 결제가 **완납·환불이 아니면** → `payment_status=paid` 자동.
- **#4**: `OrdersPage` 일괄 액션에 '증빙자료'(receipt_type/receipt_status) 추가. 기존 일괄 패턴·`domain/receiptType.ts` 재사용, 발급X→해당없음 자동. 백엔드 무변경.

## 1. #2·#3 — 백엔드 양방향 자동전환 (`backend/app/services/orders.py` `update()`)

`setattr` 적용 루프 직후, 기존 "방문일 지정→일정확정" auto 블록 **아래**에 삽입.

```python
        # #2: 완납(paid) 처리 시 자동 최종결제완료(서비스완료). 운영자가 같은 요청에서 상태를
        # 직접 지정했으면 그 값을 존중하고, 취소/이미 완료 건은 건드리지 않는다.
        if (
            changes.get("payment_status") == PaymentStatus.PAID
            and "status" not in changes
            and order.status not in (OrderStatus.CANCELLED, OrderStatus.COMPLETED)
        ):
            from_status = order.status
            order.status = OrderStatus.COMPLETED
            self.timeline.record(
                order_id=order.id,
                actor_user_id=actor_user_id,
                event_type=TimelineEventType.STATUS_CHANGED,
                title="상태 변경",
                description="완납 처리로 자동 최종결제완료(서비스완료) 전환되었습니다.",
                metadata={"from": from_status, "to": OrderStatus.COMPLETED.value, "auto": True},
            )

        # #3: 최종결제완료(서비스완료) 전환 시 자동 완납(paid). 운영자가 같은 요청에서 결제를
        # 직접 지정했으면 존중하고, 이미 완납/환불 건은 덮어쓰지 않는다.
        if (
            changes.get("status") == OrderStatus.COMPLETED
            and "payment_status" not in changes
            and order.payment_status not in (PaymentStatus.PAID, PaymentStatus.REFUNDED)
        ):
            from_payment = order.payment_status
            order.payment_status = PaymentStatus.PAID
            self.timeline.record(
                order_id=order.id,
                actor_user_id=actor_user_id,
                event_type=TimelineEventType.MEMO_ADDED,
                title="결제/정산 변경",
                description="최종결제완료(서비스완료) 전환으로 자동 완납 처리되었습니다.",
                metadata={
                    "changes": {"payment_status": {"from": from_payment, "to": PaymentStatus.PAID.value}},
                    "auto": True,
                },
            )
```

- import 추가: `from app.domain.payment_status import PaymentStatus`(기존 `PAYMENT_TRACKED_FIELDS` import 옆). `OrderStatus`·`TimelineEventType`은 이미 import됨.
- **무한루프 없음**: 두 트리거 모두 *요청(`changes`)* 기준 + "상대 필드가 요청에 없을 때만" 발동 → 자동 설정이 서로를 재발동하지 않음(단일 패스). 한 요청에 둘 다 지정하면 각자 `"X not in changes"` 가드로 미발동 → 명시값만 적용.
- **적용 범위**: `update()`를 타는 **상세 화면 + 리스트 일괄(결제 일괄변경/상태 일괄변경) 전부**. 정기 회차 생성은 `_create_line_internal`(update 미경유)이라 무영향.
- StrEnum 비교: `OrderStatus`/`PaymentStatus`는 StrEnum이라 `changes`의 문자열값과 `==`/`in` 정상 동작.

## 2. #4 — 리스트 일괄 '증빙자료' (`frontend/src/features/admin/orders/OrdersPage.tsx`)

기존 일괄 액션('상태 변경/메시지/협력사 배정/결제상태/일정 변경')과 동일 패턴:
- `bulkAction` 값에 `'evidence'` 추가. 일괄 버튼 행(`890~894` 근처)에 **'증빙자료'** 버튼(`data-testid="orders-bulk-evidence-open"`).
- `BulkActionPanel`에 `action === 'evidence'` 섹션: 1차 `receipt_type` select(현금영수증/세금계산서/카드결제/발급X) + 2차 `receipt_status` select(발급완료/미발급/해당없음). **1차=발급X → 2차 '해당없음' 고정·비활성**(상세화면 `OrderDetailPage`와 동일 규칙). 옵션·라벨은 `frontend/src/domain/receiptType.ts` 재사용.
- `handleBulkReceiptChange`: 선택 주문 루프 `updateAdminOrder(id, { receipt_type, receipt_status })`(기존 `handleBulkPaymentStatusChange` 패턴). 패널 `onApplyEvidence` 연결.
- **백엔드 무변경**: `update()`가 이미 `receipt_type`/`receipt_status`를 처리하고 `_normalize_receipt_fields`(발급X→해당없음 서버 정규화)도 적용. `AdminOrderLineInput`/`UpdateOrderInput`에 이미 receipt 필드 존재.
- 일괄 변경은 결제상태 일괄변경과 동일하게 "잔금/안내 미리보기 없음" 주석 정책 따름.

## 3. 테스트
