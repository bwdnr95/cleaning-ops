# 월 청구 정기계약 주문이 수정 저장되지 않던 오류 해결 | Tier: A

- 신고: 2026-08-25 — "정기청소-주문관리에서 주문수정 하니 `recurring_customer_payment_not_per_visit` 오류"
- 처리: 2026-08-25 완료 · 로컬 프로덕션(8002) 반영 완료 · DB 마이그레이션 없음

## 한 줄 요약

월 청구(월 정액) 정기계약 주문은 금액을 **계약에서** 관리하는데, 주문 수정 화면이 보내는
**빈 금액값**까지 서버가 거부해서 주소·방문일·요청사항 같은 **금액과 무관한 수정도 전부 막혔다.**
가드를 "값이 실제로 바뀌는 경우"에만 걸도록 고치고, 수정 화면에서는 계약이 관리하는 금액칸을 잠갔다.

## 원인 (왜 이런 오류가 났나)

1. `OrderService.update()` 의 가드가 **"payload 에 금액 필드가 있느냐"** 로 판단했다
   (`"total_amount" in changes`). 값이 비어 있어도(=아무것도 안 바꿔도) 거부했다.
2. 주문 수정 화면은 **상세상품을 고르면 단가×수량으로 소비자가·도급가를 자동 계산**해서 payload 에
   실어 보낸다. 운영자가 금액을 직접 건드리지 않아도 값이 실린다.
3. 두 가지가 겹쳐서, 월 청구 정기주문은 **수정 자체가 불가능**했다. 오류코드는 화면에 원문 그대로
   노출돼 운영자가 원인을 알 수 없었다.

## 고친 내용

### 백엔드
- 금액 가드를 **"실제 값이 실린 경우"에만** 발동하도록 변경(고객 소비자가 / 협력사 도급가·정산상태).
  빈 값은 no-op 으로 통과 → 나머지 수정이 정상 저장된다. **진짜 금액 입력은 계속 400 으로 거부**
  (계약의 월 청구액이 진실이므로 조용히 삼키지 않는다).
- 방문일이 없는 정기주문에서는 한 단계 더 엄격하게 **"지금 값과 다르면 거부, 같으면 키 자체를 제거"**.
  → 서로소 리뷰가 잡은 결함(아래) 대응.
- 주문 상세 응답에 `recurring_billing_mode` / `recurring_partner_billing_mode` 추가.
  협력사 쪽은 그 주문의 **정산 월 기준**으로 해석한 값이다. 목록 쿼리는 건드리지 않아 N+1 없음.

### 프론트엔드
- 월 청구 주문 수정 화면에서 **소비자가·할인가·계약금·잔금**(고객 월 청구 시) /
  **도급가·협력사 정산상태**(협력사 월 정산 시)를 비활성화하고 사유를 표시
  ("월 청구 정기계약 — 금액은 계약에서 관리").
- 상세상품 선택 시 **자동 계산도 원래 값으로 되돌린다**(계약금 30% 자동 산출 포함).
  화면에 보이는 값과 저장 결과가 어긋나지 않게 하기 위함.
- 저장 payload 에서 잠긴 금액 키를 제거하고, 서버 오류코드를 **한국어 안내 문장**으로 매핑
  (주문 수정 화면 + 주문 상세 결제/정산 저장 양쪽).

## 서로소 리뷰(§5)에서 잡은 결함 — 수정 완료

**[HIGH] 방문일 없는 정기주문의 정산이 지워질 수 있었다.**
`partner_payment_status: null` 을 "빈 값이니 no-op" 으로 통과시켰지만, 실제로는 그 null 이 저장되어
기존 `지급완료` 가 풀리고 이어서 `partner_settled_at`(정산일)까지 NULL 이 됐다.
→ "값이 있냐"가 아니라 **"지금 값과 다르냐"** 로 판정하도록 수정. 같은 값이면 키를 제거(진짜 no-op),
정산을 실제로 바꾸는 요청(null 로 지우기 포함)은 기존대로 `recurring_partner_payment_date_required` 거부.
회귀 테스트 `test_dateless_recurring_order_keeps_settlement_on_noop_partner_fields` 로 양방향 고정.

> 리뷰 도구 주의: `codex-collab` 이 이 머신에서 셸 실행을 전부 `blocked by policy` 로 거부한다.
> diff 를 프롬프트에 직접 실어서 리뷰를 받아야 한다(그렇게 해서 위 결함을 잡았다).

## 남은 이슈 (미수정 · 판단 대기)

**[MEDIUM] 방문일을 다른 조건의 달로 옮기는 순간 화면 잠금이 한 박자 늦다.**
상세가 내려주는 청구방식은 **저장된 방문일 기준**이라, 운영자가 방문일을 다른 조건이 적용되는 달로
바꾸면 그 자리에서 잠금이 갱신되지 않는다. 결과는 데이터 오염이 아니라 **저장 거부 + 한국어 안내**이며,
반대 방향(잠긴 채 per_visit 달로 이동)은 백엔드가 새 달 조건으로 도급가를 자동 정규화해 스스로 맞춘다.
제대로 고치려면 "날짜 변경 시 그 달의 계약 조건을 재조회하는 API" 가 필요하다.

## 불변유지 (회귀 금지)

- 월 청구 계약 주문의 `total_amount` 는 **항상 NULL** — 매출은 월 트래커(`RecurringMonthlyStatus`)에서 나온다.
- 지급완료/보류(`paid`/`hold`)이거나 `partner_settled_at` 이 있는 건의 보호 로직.
- per_visit 계약 주문의 기존 금액 입력 흐름(잠금 대상 아님).

## 고객사 답변용 문구 (그대로 복사해 쓰셔도 됩니다)

> 정기청소 주문 수정이 저장되지 않던 문제 확인해 수정 완료했습니다.
>
> **원인**: 월 정액(월 청구) 계약의 주문은 금액을 계약에서 일괄 관리하도록 되어 있는데,
> 주문 수정 화면이 금액 정보를 함께 전송하면서 시스템이 이를 "계약 금액과 충돌하는 입력"으로 보고
> 저장 전체를 막고 있었습니다. 그래서 주소·방문일·요청사항처럼 금액과 무관한 항목까지 수정이 안 됐습니다.
>
> **조치**: 실제로 금액을 바꾸는 경우에만 차단하도록 수정했고, 월 정액 계약 주문의 수정 화면에서는
> 금액 항목을 잠그고 "금액은 계약에서 관리" 안내를 표시하도록 했습니다. 금액 변경이 필요하시면
> 정기청소 > 해당 계약에서 수정하시면 되고, 월별 세금계산서·잔금·협력사 지급은 월 트래커에서
> 관리하시면 됩니다. 지금 바로 사용 가능하며, 화면 새로고침 한 번만 해주시면 됩니다.
